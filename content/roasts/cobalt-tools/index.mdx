# Cobalt: A Media Downloader That Doesn't Download Media

**Submitted by:** John
**The repo:** github.com/imputnet/cobalt
**The site:** cobalt.tools
**Score: 58/100 - Grade F**

## First Impressions

You land on cobalt.tools and the UI is refreshingly honest. One input field. A mascot. A tagline: *"a media downloader that doesn't piss you off."* No trackers, no ads, no 14-step wizard. Paste a link, get a file. The minimalism isn't laziness — it's a product philosophy expressed in markup.

The typography is clean. The dark theme doesn't feel like a dark theme checkbox — it feels deliberate. The horizontal nav (save, remux, settings, donate, updates, about) is appropriately sparse. For a tool that does one thing, the UI correctly does not try to be a platform.

Then you paste a YouTube URL.

## The Irony

YouTube is the most commonly shared video format on the internet. Cobalt supports 30+ platforms. And YouTube, the obvious flagship use case, has been completely broken on the main instance since mid-2025.

This is not a minor bug. YouTube's anti-bot infrastructure now actively blocks requests at the scale cobalt.tools operates at. The maintainers are honest about it: *"we can't go around them at our scale."* The GitHub issues are open. There's no ETA. The fix likely requires a fundamentally different architecture — decentralized, distributed, or client-side in ways the current proxy model can't accommodate.

That's a real problem. Not a *bad code* problem. A *structural constraint* problem. But if you discover it after someone hands you cobalt.tools as a YouTube downloader, you feel misled even though nobody lied to you.

The fix list for this starts with the product page, not the codebase: every instance list should clearly mark YouTube support status. Users should know before they paste.

## The Architecture Problem

Cobalt's backend is an Express-based proxy. You send it a URL, it resolves the direct media stream and tunnels it back to you. Zero caching. Privacy-first. Stateless. This is elegant for platforms that don't aggressively police third-party access.

The problem is that a centralized proxy becomes a single target. When YouTube tightens their scraping defenses, *every user of the main instance* hits the wall simultaneously. There's no fallback. No degraded mode. Just a 403.

Self-hosting is the stated answer, and the documentation for it is genuinely good — clear, Docker-first, covers DDoS protection. But "self-host it" is not a product answer. Most people who would benefit from cobalt cannot and will not run their own instance. Directing them to a community instance list is reasonable but creates the clone site problem.

## The Clone Site Problem

Because cobalt is open source and self-hostable, the internet now has dozens of cobalt instances. Some of them are maintained. Some of them serve ads. Some of them are pulling in cobalt's branding and routing downloads through infrastructure you cannot audit. There's no official instance registry with verified safety status, and the domain privacy on cobalt.tools itself contributes to a general trust ambiguity that ScamAdviser scores at 50/100.

This is the open-source media downloader's eternal dilemma: the tool that protects your privacy gets cloned by people who don't. Cobalt's brand is clean. The ecosystem around it is not.

## Mobile

The mobile experience is broken in a different way. Users report a 90% failure rate on smartphones — not just for YouTube, but across platforms. The WASM-based FFmpeg remuxing that powers on-device processing is not mobile-optimized. High data usage on failed requests. Timeout errors without clear messaging.

The SvelteKit frontend is technically sound. The Svelte bundle is small. The interface renders fine. But rendering fine is not the same as working. A tool that works on desktop and not on mobile in 2026 has a mobile problem.

## What Actually Works

Here's the honest part: when cobalt works, it's exactly what it claims to be.

**The privacy stance is genuine.** No logs, no user accounts, no tracking. Forced tunneling mode hides download sources even from your ISP. The privacy policy is three paragraphs and actually says things. This is rare.

**The UI is honest.** No dark patterns, no upsell banners, no "premium" tier. A tool that does a thing, with a UI that explains the thing, charging nothing for the thing.

**The tech is interesting.** On-device WASM remuxing is legitimately clever — cobalt streams the file and reassembles it locally without hitting cobalt's servers for processing. When it works, nothing touches your content except your own browser.

**The code is readable.** The monorepo structure (`api/`, `web/`, `packages/api-client/`) is clean. The TypeScript coverage is solid. The self-hosting docs are better than most commercial products write for their own onboarding.

**30+ platforms.** TikTok, Reddit, Twitter, Vimeo, SoundCloud, Twitch — many of these still work on the main instance. For everything-except-YouTube, cobalt is frequently the right tool.

## Fixes

**The product issues:**

1. **Surface YouTube status prominently.** Not buried in a GitHub issue — on the landing page, on the input field. "YouTube: degraded on this instance." Users who know upfront will self-select to self-host or use an alternative. Users who find out after three failed attempts just leave angry.

2. **Verify and publish an instance registry.** A cobalt-maintained page of known-good instances with health status, YouTube support, and last-verified date. Community trust doesn't scale on reputation alone.

3. **Fix mobile or document the limitation.** Either invest in mobile-optimized WASM builds, or put "optimized for desktop" somewhere a user will see it before they try on their phone.

**The architectural issues:**

4. **Explore a client-side extraction path.** Browser extensions, native apps, or a browser-native approach that shifts the YouTube request from cobalt's server to the user's own IP. This sidesteps the scale problem entirely. The team knows this — there's discussion in the GitHub issues. It's the right direction.

5. **Batch and playlist support.** Every competitor has it. One link at a time is fine for casual use; it's a dealbreaker for anyone with a workflow.

## Verdict

58/100. The score isn't about the code — the code is good. It's about the product delivering on its promise.

"A media downloader that doesn't piss you off" is a great tagline. But a media downloader that can't download from the world's largest video platform, doesn't work reliably on phones, and produces an ecosystem of unverifiable clones does, eventually, piss you off. Not through bad design. Through structural limitations that have caught up with the model.

The good news is that none of these problems are unsolvable. The architecture needs rethinking for YouTube specifically. The mobile story needs investment or honesty. The instance ecosystem needs curation. The team clearly cares — the privacy stance and the code quality both prove that. They just need to match the honesty of the UI with equally honest expectation-setting around what the main instance can and can't do right now.

The minimalist UI promised a tool that works. Make the tool work, and the UI can stay exactly as it is.

**Overall Score: 58/100 - Grade F**
