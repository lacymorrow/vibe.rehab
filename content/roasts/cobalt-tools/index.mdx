# Cobalt: A Media Downloader That Doesn't Download Media

**Submitted by:** John
**The repo:** github.com/imputnet/cobalt
**The site:** cobalt.tools
**Score: 58/100 - Grade F**

## First Impressions

You land on cobalt.tools and I have to say, the UI is refreshingly honest. One input field. A little mascot. A tagline that reads *"a media downloader that doesn't piss you off."* No trackers, no ads, none of the 14-step wizard nonsense. You paste a link, you get a file. The minimalism here isn't laziness, it's a point of view someone actually committed to.

The typography is clean. The dark theme doesn't feel like somebody ticked a "dark mode" checkbox and called it a day, it feels deliberate. The nav across the top (save, remux, settings, donate, updates, about) is sparse in a good way. For a tool that does one thing, this is exactly right - it doesn't try to become a platform.

Then I pasted a YouTube URL.

## The Irony

YouTube is the single most shared video source on the internet, and cobalt supports 30+ platforms, so you'd assume it's the flagship. Except YouTube has been flat-out broken on the main instance since mid-2025.

And this isn't a little bug you can patch on a Friday. YouTube's anti-bot infrastructure actively blocks requests at the scale cobalt.tools runs at. The maintainers don't hide from it either - they straight up say *"we can't go around them at our scale."* The GitHub issues are open, there's no ETA, and the real fix probably means a completely different architecture (decentralized, distributed, or shoved client-side in a way the current proxy just can't do).

So it's a legitimate problem, but it's a structural one, not a "your code is bad" one. Trouble is, if someone hands you cobalt.tools as a "YouTube downloader" and you find out the hard way, you feel misled - even though technically nobody lied to you.

The fix here starts on the product page, not in the codebase. Every instance list should say, plainly, whether YouTube works. Tell people before they paste, not after.

## The Architecture Problem

Under the hood, cobalt's backend is an Express proxy. You hand it a URL, it resolves the direct media stream, and it tunnels the file back to you. No caching, no state, privacy-first. For platforms that don't obsess over third-party access, that design is genuinely elegant.

The catch is that one centralized proxy is also one big target. The moment YouTube tightens its defenses, everybody on the main instance hits the same wall at the same second. No fallback, no degraded mode, just a 403 staring back at you.

Self-hosting is the official answer, and honestly the docs for it are good - clear, Docker-first, they even cover DDoS protection. But "go host it yourself" isn't really a product answer. The vast majority of people who'd love cobalt are never going to spin up their own instance. Pointing them at a community instance list is a fair compromise, but it opens up the clone problem.

## The Clone Site Problem

Because cobalt is open source and easy to self-host, the internet is now littered with cobalt instances. Some are well maintained. Some run ads. And some grab cobalt's branding and route your downloads through infrastructure you have no way to inspect. There's no official registry saying "these instances are verified safe," and the domain privacy on cobalt.tools itself feeds into the general trust fog (ScamAdviser puts it at 50/100).

It's the eternal catch-22 for privacy-focused tools: the thing you built to protect people gets cloned by people who won't. Cobalt's own brand is clean. The neighborhood that's grown up around it is not.

## Mobile

Mobile is broken in a different, more annoying way. People report roughly a 90% failure rate on phones, and not just on YouTube - across the board. The WASM FFmpeg remuxing that handles on-device processing just wasn't tuned for mobile. You get high data usage on requests that fail anyway, and timeouts with no real explanation.

The SvelteKit frontend itself is fine. The bundle is small, the interface renders cleanly. But rendering cleanly and actually working are two different things, and a tool that's great on desktop and dead on mobile in 2026 has a real gap to close.

## What Actually Works

Here's the thing though - when cobalt works, it is exactly what it says on the tin.

**The privacy stance is the real deal.** No logs, no accounts, no tracking. Forced tunneling mode hides your download sources even from your ISP. The privacy policy is three short paragraphs that actually commit to something, which is rarer than it should be.

**The UI is honest.** No dark patterns, no upsell banners, no fake "premium" tier lurking behind a button. It does a thing, the UI explains the thing, and it charges you nothing for the thing.

**The tech is genuinely cool.** On-device WASM remuxing is a clever move - cobalt streams the file and reassembles it right there in your browser, so cobalt's servers never touch your content during processing. When it works, nothing sees your file but you.

**The code reads well.** The monorepo layout (`api/`, `web/`, `packages/api-client/`) is tidy, the TypeScript coverage holds up, and the self-hosting docs are better than what most paid products write for their own onboarding.

**30+ platforms.** TikTok, Reddit, Twitter, Vimeo, SoundCloud, Twitch - a lot of these still work fine on the main instance. For basically-everything-except-YouTube, cobalt is often the tool I'd reach for.

## Fixes

**The product issues:**

1. **Surface YouTube status where people can see it.** Not buried three clicks deep in a GitHub issue - put it on the landing page and near the input field. Something like "YouTube: degraded on this instance." People who know upfront will happily self-host or grab an alternative. People who find out after three failed attempts just leave mad.

2. **Verify and publish an instance registry.** A cobalt-maintained page of known-good instances with health status, YouTube support, and a last-verified date. You can't scale community trust on vibes alone.

3. **Fix mobile, or at least admit the limitation.** Either put real work into mobile-optimized WASM builds, or slap "optimized for desktop" somewhere a person sees it before they try it on their phone.

**The architectural issues:**

4. **Chase a client-side extraction path.** Browser extensions, native apps, or a browser-native approach that moves the YouTube request off cobalt's server and onto the user's own IP. That sidesteps the whole scale problem. The team already knows this - it's being kicked around in the GitHub issues - and it's the right direction.

5. **Add batch and playlist support.** Every competitor has it. One link at a time is fine when you're grabbing a clip; it's a dealbreaker the second anyone has an actual workflow.

## Verdict

58/100. And to be clear, the score isn't a knock on the code - the code is good. It's about whether the product delivers on what it promises.

"A media downloader that doesn't piss you off" is a great line. But a downloader that can't touch the world's biggest video site, flakes out on phones, and spawns a swarm of clones you can't verify does, eventually, piss you off. Not because anyone designed it badly. Because the model ran into limits that finally caught up with it.

The upside is that none of this is unfixable. YouTube needs an architecture rethink. Mobile needs either investment or honesty. The instance ecosystem needs curation. And this team obviously cares - the privacy stance and the code quality both give that away. What's missing is matching the honesty of the UI with equally honest expectations about what the main instance can and can't do right now.

The minimalist UI promised a tool that works. Make the tool work, and the UI can stay exactly as it is.

**Overall Score: 58/100 - Grade F**
